# 电商售后 Agent · 面试演示指南

> 一个把「感知 + ReAct 推理 + 工具调用 + 人工审批 + 记忆 + 子代理 + 会话状态机」全部落地的**电商售后客服 Agent**。
> 本文档是面试现场演示脚本 + 追问应答手册。演示前请按「环境准备」跑通一遍。

---

## 一、一句话定位

> "这不是一个通用聊天机器人——它是一个**能接入订单系统、按规则引擎判定售后资格、高风险操作走人工审批、并能转人工的电商售后客服 Agent**。豆包只能聊，它能'办成售后退款这件事'。"

---

## 二、环境准备（演示前必做）

```bash
cd D:\1_code\agent_forJD
uv run agentmind          # 打开 http://127.0.0.1:8765
```

**必须预先验证**（确保面试现场不翻车）：
1. WebUI 能打开、模型能正常回复（`你好`）
2. 问一句 `帮我查一下 JD20260801001 这个订单` → 看到工具卡片 + 真实数据
3. 说 `我要退 JD20260801001` → 出现**审批弹窗**，点允许 → 出现退单号
4. 语音条可点播（`用语音回答我：你好`，绿色语音条出现）

> ⚠️ 网络风险：`price_compare`（比价）依赖联网搜索，面试现场网络不稳时不要展示，或提前说明"演示机网络受限，比价子代理暂不展示"。退货/查单/审批/政策/转人工**全部不依赖外网**，最稳。

## 三、演示脚本（15 分钟完整流程）

### 开场（1 分钟）

> "我做的这个项目叫 AgentMind，是一个完整的 Agent 框架。今天重点展示它落地的一个真实业务场景——**电商售后客服**。它具备：查订单、按平台规则判定退货资格、高风险退款走人工审批、售后政策问答、用户画像差异化服务、以及转人工和会话状态管理。"

### 场景 1 · 订单查询（1 分钟）

**你说**：`帮我查一下 JD20260801001 这个订单`

**预期**：模型调用 `order_lookup` → 展示工具卡片 → 返回小米手环 9、¥249、已签收、收货地址等真实数据。

**讲解点**："模型没有编造，它通过工具读取了订单系统的真实数据——这就是感知（Perception）。"

### 场景 2 · 退货 + 人工审批（核心，3 分钟）

**你说**：`我要退 JD20260801001 这个订单，帮我办一下`

**预期**：
1. 模型先调 `after_sales_check` → 规则引擎判定"七天无理由，¥249"
2. 再调 `after_sales_apply` → **弹出审批框**（"该工具会修改真实状态…允许/拒绝"）
3. **你现场点"允许"** → 生成退单号 `AS…`，退款 ¥249

**讲解点**（最加分的一段）：
> "注意看这个审批弹窗——退款是高风险操作，我不让模型自己拍板，而是**人工审批**。这对应电商真实的风控需求：高金额退款、改价、补发都要人工确认。**超时或拒绝，退款就不会执行**，这是安全默认值。"

### 场景 3 · 规则引擎拒绝（1.5 分钟）

**你说**：`JD20260801002 能退吗？`

**预期**：模型调 `after_sales_check` → 返回"已签收 25 天，超过最长退货期限 15 天，无法退货"。

**讲解点**：
> "这里我要强调一个设计：**退货资格不是模型判断的，是一个独立的规则引擎**——7 天无理由、15 天上限、重复售后拦截、高金额风险分级。模型只负责理解用户意图，资格判定是确定性的业务规则。这是生产级售后 Agent 的分水岭，不能靠 LLM 拍脑袋。"

### 场景 4 · 用户画像差异化服务（2 分钟）

**你说**：`我是张三，JD20260801004 这个 MacBook 想退`

**预期**：
1. `after_sales_check` → 符合条件，且附加 **"👤 用户等级：金卡会员"**（画像提示）
2. 模型可能再调 `user_profile` 确认画像
3. `after_sales_apply` → ¥8999 高金额，审批弹窗 → 允许 → 退单号

**讲解点**：
> "售后结果里自动带了用户画像——张三消费 1.2 万，是金卡会员。系统会给他差异化服务。画像来自消费数据 + 偏好存储，`user_profile` 工具可以随时查。"

### 场景 5 · 售后政策问答（RAG，1.5 分钟）

**你说**：`退货运费谁出？退款多久到账？`

**预期**：模型调 `after_sales_policy` → 返回"七天无理由退货运费买家承担（有运费险保险赔付）"、"审核 1-3 个工作日，原路退回，微信/支付宝实时到账"。

**讲解点**：
> "政策没有写死在模型里，而是放在一个**政策知识库**里做检索（RAG）。这样政策变了只改文档，模型永远不会背错政策——可维护、可扩展。"

### 场景 6 · 转人工 + 会话状态（2 分钟）

**你说**：`你们处理得太慢了，我很不满意，我要投诉！`

**预期**：
1. 模型调 `escalate_human` → 生成工单号 `TS…`
2. 顶部徽章变为 **客服 · 已转人工**

**再问**：`好的，人工已经联系我了，问题解决了，谢谢`

**预期**：模型调 `resolve_issue` → 徽章变为 **客服 · 已解决**

**讲解点**：
> "整个客服会话有一个**状态机**：待处理 → 处理中 → 已解决 / 已转人工。处理中超时会自动升级人工。右上角能看到实时状态。这保证每一条客服工单都有生命周期，可追踪、可审计。"

### 场景 7 · 记住偏好（1 分钟）

**你说**：`记住我退款希望电话联系`

**预期**：模型调 `remember_preference` → "已记住 张三 的偏好：退款希望直接电话联系"

**讲解点**："偏好写进用户画像，下次服务这个用户时自动带出来。"

### 场景 8 · 语音回执（可选，1 分钟）

**你说**：`用语音回复我：您好，京东售后客服为您服务`

**预期**：模型调 `mcp_voice_voice_speak` → 出现**绿色语音条**，点击播放；回答还会自动生成语音（auto_voice）。

**讲解点**："语音条像微信一样持久化，切会话/刷新后还能点播。"

## 五、面试追问应答（背熟）

**Q1：退货资格为什么不用大模型判断？**
> 资格判定是确定性业务规则（期限、金额、状态），LLM 判断会不稳定、还可能被诱导。我把规则抽成独立引擎，模型只做意图理解。生产上这是必然选择。

**Q2：审批超时/拒绝会怎样？**
> 按拒绝处理（安全默认值）。模型收到"用户拒绝了该工具调用"，会如实告知用户并给出替代方案，不会假装执行。

**Q3：会话状态机解决了什么问题？**
> 工单生命周期管理：每个会话都有状态，处理中超时自动升级人工，可追踪可审计。真实客服系统都有 SLA 和超时升级。

**Q4：mock 开放平台怎么换成真实的？**
> 工具只依赖 `MockEcommerceAPI` 这个边界（接口契约对齐京东开放平台风格），换成真实 HTTP client 即可，工具层和规则引擎完全不用动——这就是架构里"业务系统接入层"的意义。

**Q5：政策为什么用 RAG 检索而不是写死在提示词？**
> 政策经常变。RAG 让政策以文档形式存在，改政策不改代码、模型不会背错、还能扩展任意多条。

**Q6：比价为什么用子代理？**
> 比价是独立子任务，子代理跑在隔离上下文里，只把浓缩结果返回给主 Agent——主上下文不会因为大量搜索结果而膨胀。深度受限防递归。

**Q7：这跟通用聊天机器人有什么区别？**
> 通用机器人只能对话，不能访问订单系统、不能执行退款、没有风控审批。我的 Agent 是**能办成业务的**，聊天只是外壳。

## 六、差异化亮点（讲这三点就够）

1. **LLM 理解 + 规则引擎决定** —— 资格判定是确定性的，模型不背政策、不拍脑袋。
2. **高风险操作人工审批 = 电商风控** —— 退款/改价必须审批，超时拒绝是安全默认。
3. **从"聊天"到"行动闭环"** —— 查真数据、办真事、有会话生命周期、有合规兜底。

## 七、如果现场网络不稳（应急预案）

- 展示顺序调整：**只做 场景1/2/3/6**（完全本地，不依赖外网）+ 场景8（语音，需 edge-tts 网络）
- 比价（场景9）和网页搜索**跳过**，说"演示机网络受限"
- 语音若不响（edge-tts 被墙）：说"语音能力已实现，当前网络到微软语音端点不可达"——**如实说明比硬演更有说服力**
- 手边常备：`uv run agentmind` 启动后先自测一遍再开始面试
